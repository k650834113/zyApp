# 小程序会员明细、等级同步与月卡微信支付设计

> 决策日期：2026-07-26
> 适用分支：`codex/member-recharge-pc-transactions`
> 发布约束：先发布隔离测试 API、体验版小程序和 PC 测试更新通道；体验验收前不合并、不推送 Git、不更新生产 API 或生产 PC 通道。

## 1. 目标

本轮同时解决以下五项体验问题：

1. 首页会员姓名和等级被“编辑”按钮挤压。
2. 小程序明细不显示 PC 线下现金充值及冲正。
3. PC 本地会员等级与小程序读取的云端等级不一致。
4. 顾客不能在小程序中使用微信支付开通或续费月卡。
5. 页面内容区重复显示原生导航栏已有的页面标题。

月卡区域必须比现有单行状态更醒目，成为首页独立重点卡片。

## 2. 已确认业务规则

- 月卡使用微信直接支付，禁止使用储值余额购买。
- 月卡方案优先读取商户模板和门店覆盖；未配置时使用 200 元、30 天、门店范围的默认方案。
- 创建支付订单时冻结方案名称、价格、天数和适用范围快照，后续配置变化不得改变待支付订单。
- 无有效月卡或月卡已过期时，支付成功后立即开通。
- 有效月卡续费时，从当前到期时间顺延方案天数。
- 暂停月卡不允许顾客自行续费，页面提示联系店员恢复。
- 微信支付只增加月卡权益，不得写入本金或赠送钱包。
- 体验版与正式版使用同一套页面、接口和支付逻辑，只隔离 API、门店、数据库、Redis、订单前缀和支付回调环境。

## 3. 方案选择

采用独立月卡支付订单方案。

不复用 `wechat_recharge_order`，因为储值充值结算会写钱包账本，复用后容易把月卡款误记为储值。也不采用“支付成功后提交 PC 命令”，因为该方案依赖 PC 在线并会造成顾客支付成功但权益延迟。

新增月卡订单只复用现有微信支付适配器、签名验签和主动查单能力。月卡订单、月卡投影、月卡事件、审计和支付回调收件箱保持独立语义。

## 4. 小程序界面

### 4.1 首页会员头部

- 删除内容区的“会员中心”标题，保留微信原生导航栏标题。
- 头像右侧使用可收缩的身份信息区域。
- 姓名超长时省略，等级使用独立标签，不再与姓名和按钮共同抢占固定宽度。
- “编辑”改为右侧固定宽度的小型描边按钮。
- 340px 及更窄屏幕仍显示等级，不再通过媒体查询隐藏实际会员等级。

### 4.2 醒目月卡卡片

在余额卡与微信储值充值卡之间增加独立月卡卡片：

- 顶部显示“会员月卡”和当前状态标签。
- 未开通时突出显示 `¥200 / 30天` 或实际门店方案。
- 已开通时突出显示到期日，并显示续费后将顺延的天数。
- 主按钮使用“立即开通”或“微信续费”，与储值充值按钮视觉层级一致。
- 暂停状态显示醒目提示，但禁用顾客续费按钮。
- 支付中、支付取消、订单待确认、支付成功和订单过期均显示明确反馈。

### 4.3 重复标题

- 明细页删除内容区“全部明细”，筛选栏直接位于页面顶部。
- 资料编辑模式删除内容区“我的资料”标题和说明。
- 新会员首次注册仍保留“完善会员资料”及说明，避免失去注册上下文。
- 所有页面继续保留微信原生导航栏标题。

## 5. 线下充值明细

`MemberSelfServiceHistory.activities` 增加对云端钱包流水的投影：

- `wallet.cash_recharged` 显示为“线下充值”，金额为本金加赠送，方向为收入，状态为“已到账”。
- `wallet.cash_recharge_reversed` 显示为“线下充值冲正”，金额使用被扣回的绝对值，方向为支出，状态为“已冲正”。
- `wallet.wechat_recharged` 继续由微信充值订单生成，不再从钱包流水重复生成。
- 消费单、月卡事件和微信充值的原排序规则保持不变；所有活动按发生时间统一倒序并限制 100 条。

共享契约增加 `reversed` 活动状态，小程序首页和明细页都映射为“已冲正”。

## 6. 会员等级同步

云端等级不同步的根因是 PC 现金充值和冲正只同步钱包事件，没有同步本地 `membership_grant` 计算后的会员等级。

修复采用本地真实资格投影，不根据云端充值金额猜测最终等级：

1. PC 完成现金充值或充值冲正时，在同一 SQLite 事务中追加会员等级对账 outbox。
2. 对账载荷包含会员 ID、由全部未撤销资格计算出的 `ordinary | advanced`、发生时间和原因。
3. 云端按租户和会员加锁，追加会员事件和审计后更新 `cloud_member.tier`。
4. 云端会员更新改为租户级，不再要求会员原始 `store_id` 与本次发生门店一致。
5. PC 更新后执行一次幂等历史等级对账，为当前门店全部会员排队生成等级投影；完成标记保存在本地数据库，异常重启可安全重试。
6. 现有微信充值产生的高级会员资格继续保留，现金充值冲正只根据 PC 本地全部有效资格计算最终等级，不会错误移除手工、活动或其他充值来源。

这样可以修复已经存在的等级差异，也能保证后续充值和冲正持续同步。

## 7. 月卡支付订单与结算

### 7.1 云端数据

新增 `wechat_monthly_card_order`：

- 订单、租户、门店、会员、微信身份和请求幂等键。
- 商户单号和微信交易号。
- 方案名称、价格、天数、适用范围快照。
- `creating | pending_payment | settled | failed | expired` 状态。
- 客户端支付参数、过期时间、支付时间、结算时间和错误信息。
- 若为续费，保存结算时命中的月卡 ID 和续费前后到期时间。

支付回调收件箱增加月卡订单关联，仍按微信事件 ID 幂等。充值订单和月卡订单使用不同单号前缀，回调处理器据此进入对应结算服务。

### 7.2 顾客接口

- `GET /v1/member/monthly-card-configuration`：返回当前方案、会员月卡状态和是否允许购买。
- `POST /v1/member/monthly-card-orders`：创建幂等月卡微信支付订单。
- `GET /v1/member/monthly-card-orders/:orderId`：查询订单并在必要时主动向微信查单。

所有接口要求已绑定且启用的会员身份。月卡购买不受储值年龄资格限制，因为它不是钱包储值，但仍要求会员状态有效。

### 7.3 可信结算

支付回调或主动查单确认成功后，在一个 PostgreSQL 事务中：

1. 校验商户号、AppID、付款 OpenID、商户单号和支付金额。
2. 锁定月卡订单和会员当前月卡。
3. 无有效月卡时创建新月卡；已过期月卡按当前时间重新开通。
4. 有效月卡从原到期时间顺延；暂停月卡拒绝在创建订单阶段购买。
5. 追加 `monthly_card.purchased` 事件，载荷包含订单、方案和续费前后日期快照。
6. 更新订单为 `settled`，追加云端事件和审计。
7. 重复回调、重复查单或客户端重复查询只返回同一结果，不重复延长。

本轮不新增顾客自助退款入口。订单保留微信交易号和完整购买快照，现有现金月卡退款路径不得把微信月卡误判为现金；微信原路退款作为独立财务发布任务处理。

## 8. PC 镜像与测试更新

- PC 云镜像能够读取微信月卡的 `payment_method = 'wechat'`，共享契约和 SQLite 约束允许 `cash | wechat`。
- PC 月卡明细显示微信购买事件和真实支付方式，不把微信月卡显示成现金。
- 新月卡订单作为桌面镜像资源保留，便于后续对账和原路退款扩展。
- 本轮 PC 安装包只发布到测试更新通道；生产 PC 通道在体验版和 PC 测试版共同验收后再发布。

## 9. 错误处理

- 用户取消微信支付：订单保留为待支付或由微信结果转为关闭，不增加月卡。
- 微信返回成功但客户端断网：重新进入首页后通过订单查询或回调完成结算。
- 订单金额或付款人不匹配：拒绝结算并记录错误，不修改月卡。
- 配置不存在或格式非法：接口返回不可购买，禁止静默使用错误价格。
- 会员在支付期间被停用：结算拒绝并记录需人工处理状态。
- 支付期间月卡状态发生变化：结算时重新锁定并计算；若变为暂停则不自动续费，记录需人工处理。

## 10. 测试与验收

自动测试至少覆盖：

- 320px、375px 和常见大屏宽度下姓名、等级和编辑按钮均可见。
- 三个页面不再重复显示内容标题，新会员注册标题仍存在。
- 线下充值、冲正、微信充值不重复并按时间正确排序。
- 现金充值升级、冲正降级、多资格保级和历史等级幂等对账。
- 月卡默认方案、门店覆盖、首次开通、有效期顺延、暂停拒绝。
- 支付创建、取消、主动查单、回调验签、金额/OpenID 校验和重复结算。
- 月卡支付不产生任何钱包账本记录。
- PC 镜像正确显示微信月卡支付方式和购买事件。
- 小程序类型检查、单元测试、生产体验构建及完整工作区回归。

人工验收顺序：

1. 发布测试 API，确认生产 API 和 Caddy 容器未重启。
2. 发布 PC 测试更新通道并在测试环境同步等级。
3. 构建 `production-test-wechat` 体验版。
4. 使用 0.01 元储值继续验证原充值通道未回归。
5. 使用真实 200 元月卡支付验证开通，再验证有效月卡续费顺延。
6. 核对小程序、测试 PC 和测试数据库中的等级、月卡和明细一致。
7. 用户确认后再决定合并、Git 推送、生产 API 和生产 PC 更新。
