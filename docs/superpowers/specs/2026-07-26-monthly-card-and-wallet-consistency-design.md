# 月卡有效期主视觉与 PC/小程序账务一致性修复设计

日期：2026-07-26
目标版本：0.23.2
适用范围：小程序首页、PC 测试环境 SQLite、测试 API 与 PC 云端同步

## 1. 已确认需求

- 未开通月卡的会员继续看到醒目的月卡价格和微信开通按钮。
- 已开通月卡的会员以到期日期作为月卡卡片主视觉，同时显示剩余天数。
- 已开通月卡时，续费价格和续费按钮保留，但降为次要操作。
- PC 测试端线下充值、储值消费、余额和交易流水必须与同门店小程序一致。
- 修复必须保留追加式财务记录、操作人鉴权和环境隔离，不得直接改余额或删除真实账本。
- 只更新测试 API、PC 测试更新通道和小程序体验构建；生产服务和远程 Git 保持不变。

## 2. 调查证据与根因

### 2.1 环境一致

本机 PC 当前活动环境为 `test`，活动门店为测试桌游吧。小程序
`production-test-wechat` 配置使用相同的测试门店 ID 和
`https://judian.icu/test`，因此问题不是门店或数据库选错。

### 2.2 同步队列被无操作人的等级对账阻塞

0.23.1 启动同步时会在员工登录前执行历史会员等级对账。该过程生成的
`member.tier.reconciled` 操作没有 `actor_id`，但同步 API 对所有非系统业务命令
要求有效员工操作人。

当前设备序列 1–20 已确认，21–30 待确认。序列 21 是无操作人的等级对账，
云端持续返回 `Business sync command requires an actor`。设备序列按顺序确认，
所以后续现金充值、等级变化、储值消费和订单均不能越过序列 21。

当前被测会员本机余额为 120.01 元，云端余额为 60.02 元。差额对应本机尚未
上传的现金充值 100 元和储值消费 40 元；云端另有一笔 0.01 元微信充值。

### 2.3 微信充值单镜像查询类型不匹配

PC 拉取 `wechat_recharge_orders` 时，将 PostgreSQL 的
`cloud_wallet_ledger.source_operation_id` 文本字段直接与
`wechat_recharge_order.id` UUID 字段比较，触发 `operator does not exist:
text = uuid`。PC 因此回退到本地镜像，无法可靠刷新最新微信充值单。

### 2.4 本地财务流水保存了云端回声副本

PC 本地完成财务操作后保留原始 SQLite 账本。操作上传云端后，PC 又按云端
`operation_id` 插入一条回声账本。两条记录具有相同的租户、会员、事件类型、
业务来源和金额，但 ID 不同，导致 PC 储值流水和报表重复。

这些回声记录不是第二次业务交易，但已经作为技术镜像写入本地表。修复必须
保留原始证据，不能把真实财务记录与回声混在一起直接批量删除。

## 3. 小程序月卡状态设计

### 3.1 未开通

沿用 0.23.1 的橙金色月卡卡片：

- 月卡方案名；
- 大号价格和有效天数；
- 醒目的“微信开通月卡”按钮；
- 支付成功后立即生效的说明。

### 3.2 已开通

卡片改为权益状态优先：

- 顶部显示“月卡生效中”状态标识；
- 主视觉显示“有效期至”及大号 `YYYY-MM-DD`；
- 日期旁或下方显示按本地自然日计算的“剩余 N 天”；
- 方案价格和“续费后从当前到期日顺延”作为次要说明；
- “微信续费”使用较小的次要按钮，不再占满卡片宽度。

剩余天数仅用于展示，到期判断继续以服务端返回的 ISO 到期时间为准。为避免
时区临界误差，展示按 `Asia/Shanghai` 自然日计算，最低显示 0 天。

### 3.3 暂停

暂停月卡仍以到期日期为主视觉，但显示“已暂停”标识和联系门店恢复提示。
续费按钮禁用，不改变现有业务限制。

## 4. 同步与账本修复设计

### 4.1 补齐历史等级对账操作人

SQLite Schema 29 增加一次性修复：

- 只处理 `sync_status = 'pending'`、
  `operation_type = 'member.tier.reconciled'` 且 `actor_id IS NULL` 的记录；
- 从同租户同门店的有效本地员工中选择操作人，优先有效店长，其次有效店员；
- 只补齐 outbox 的鉴权操作人，不修改业务载荷、载荷哈希、设备序列、会员资料
  或等级值；
- 如果没有有效员工则保持原记录不变，由同步状态明确报告，禁止绕过云端鉴权。

历史等级对账生成逻辑同步改为在生成前解析有效员工并写入 `actor_id`，避免新安装
再次生成无操作人的队列项。人工充值后产生的等级对账继续使用当前登录员工。

### 4.2 修复微信充值镜像

API 镜像查询把 `wechat_recharge_order.id` 显式转换为文本后再与
`source_operation_id` 比较。查询仍为租户范围，钱包操作关联仍只接受同租户、
事件类型为 `wallet.wechat_recharged` 的记录。

### 4.3 阻止新的账本回声重复

PC 物化云端钱包流水时，除按云端 `operation_id` 幂等外，再按以下业务键检查：

- `tenant_id`
- `member_id`
- 映射后的本地 `entry_type`
- `source_operation_id` 对应的本地 `source_id`
- 本金和赠送金变动金额

若已存在非 `cloud-sync` 的本地原始账本，则将该云端记录视为本机操作的确认回声，
不再插入第二条 `wallet_ledger`。来自小程序或其他 PC、且没有匹配本地原始记录的
云端流水仍正常插入。

### 4.4 兼容已存在的回声记录

不删除已写入的财务行。PC 储值流水与经营报表读取时，隐藏满足以下条件的
`cloud-sync` 回声：

- 存在相同业务键和金额的非 `cloud-sync` 本地原始账本。

原始本地账本保留展示；纯云端来源的微信充值、其他设备操作和没有本地对应项的
云端账本继续展示。诊断导出和 SQLite 原表仍保留所有技术记录，便于审计和追查。

## 5. 修复后的数据流

1. PC 0.23.2 打开测试库并迁移到 Schema 29。
2. 迁移为当前 6 条无操作人的等级对账补齐合法员工 ID。
3. 同步从设备序列 21 继续按序上传。
4. 云端确认等级、现金充值、消费和订单操作。
5. 云端钱包余额更新为全部已确认增量的结果。
6. 小程序重新获取会员摘要和历史，显示同一云端余额与账单。
7. PC 拉取钱包、订单和微信充值镜像；本机操作的云端回声不再形成重复流水。
8. PC 与小程序分别从本地镜像和云端主库展示相同业务结果。

不通过手工 SQL 改写余额，不跳过设备序列，也不重新执行充值或消费。

## 6. 错误处理

- 找不到有效本地员工时，不补齐操作人，保留待同步状态并显示可诊断错误。
- 云端员工已停用或无门店权限时，API 继续拒绝操作，不允许设备令牌代替员工权限。
- 微信充值镜像查询失败时继续保留既有本地回退，但日志记录资源和错误。
- 云端回声判定必须同时匹配业务来源、类型、会员和金额；信息不完整时宁可保留，
  不错误隐藏潜在的真实第二笔交易。

## 7. 自动测试

### 小程序

- 未开通状态仍显示大价格和大开通按钮。
- 已开通状态显示大号到期日期和剩余天数。
- 已开通状态的续费按钮为次要尺寸。
- 暂停状态显示到期日期、暂停提示并禁用续费。
- 上海时区下当天、跨日和已到期的剩余天数计算正确。

### SQLite 与同步

- Schema 28 升级到 29 后，只补齐待同步且缺少操作人的等级对账。
- 有效店长优先于店员；没有有效员工时不修改。
- 新生成的历史等级对账具有有效 `actor_id`。
- 修复后的设备序列可继续确认后续现金充值和消费。

### 镜像与账本

- 微信充值镜像 SQL 使用兼容的文本比较。
- 本机原始账本存在时不插入云端回声副本。
- 小程序或其他设备产生的云端流水仍会插入。
- 已存在回声时，PC 储值流水和报表只计算一次。
- 本金、赠送金、冲正和消费分别验证，不通过仅时间接近来去重。
