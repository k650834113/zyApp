# 小程序已验收测试版整体合并与生产库切换设计

> 决策日期：2026-07-29
>
> 状态：已确认并进入实施
>
> 适用范围：`main`、`codex/member-recharge-pc-transactions`、`codex/miniapp-production-recharge`

## 1. 目标

按两个可独立验证的阶段恢复正确的小程序发布基线：

1. 先将 `codex/member-recharge-pc-transactions` 整体合并到 `main`，保留已经确认的新版会员界面、配套 API、共享合同、PC 交易记录、云同步和财务一致性修复。
2. 在测试 API `https://judian.icu/test` 上完成自动化验证并生成测试构建，证明新版界面仍使用隔离测试环境。
3. 再把 `codex/miniapp-production-recharge` 中正式发布所需的能力按提交顺序移植到更新后的 `main`，不得用旧分支页面覆盖新版会员界面。
4. 生成只访问 `https://judian.icu` 和正式门店的 `production-wechat` 构建，作为后续微信体验版上传与人工验收的候选产物。

本次不执行服务器 SSH 部署、微信开发者工具上传、真实付款、商户平台对账、审核或发布。

## 2. 已确认的合并范围

测试版采用整分支合并，不仅选择小程序 UI 文件。以下内容作为同一已验收候选版本进入 `main`：

- 原生小程序新版会员首页、明细页和“我的”页面。
- 会员资料、头像、充值、月卡和统一历史记录客户端逻辑。
- `@zyapp/contracts` 对应接口。
- NestJS 会员自助、充值、支付、同步与投影逻辑。
- PC 交易记录、收银手动刷新和云端充值对账能力。
- 钱包镜像去重、月卡同步和充值规则一致性修复。
- 0.23.2 候选版本及发布契约测试。
- 已有规格、计划与验收文档。

未跟踪文件 `infra/deploy/production.env.before-domain-20260725` 属于用户现有文件，不读取其秘密内容、不修改、不暂存、不提交。

## 3. 方案选择

采用“测试版整分支合并，生产能力逐提交移植”的分阶段方案。

### 3.1 测试版阶段

将 `codex/member-recharge-pc-transactions` 通过一个明确的非快进合并提交并入 `main`。当前 `main` 在共同祖先之后只有生产验收设计和计划文档，预计不会与测试版业务代码产生大范围冲突；如发生冲突，逐文件确认，不能以整侧覆盖处理。

### 3.2 生产阶段

不直接把旧基线上的生产分支一次性合并。按原顺序移植以下提交：

1. `fa6d252`：下发权威充赠规则。
2. `fe13340`：计算小程序充赠预估。
3. `5120857`：展示预计赠送和规则说明。
4. `fbcdca6`：增加正式小程序构建。
5. `f3869c4`：启用正式微信支付配置。
6. `7d76ee4`：增加正式部署防误操作保护。
7. `82c1c84`：补充正式验收文档。

逐提交移植可以把接口、页面、构建和部署冲突分开处理。发生冲突时遵守以下优先级：

1. 保留新版会员三页面信息架构和视觉样式。
2. 保留测试版中较新的充值金额、自定义充值、支付查询、月卡和历史记录流程。
3. 引入生产分支的权威充赠规则数据源、实时预估和规则弹窗，但不得恢复旧首页结构。
4. 引入独立 `production-wechat` 模式、正式端点、正式门店、正式支付和部署防护。
5. 不恢复 0.01 元专用卡片、虚拟手机号、开发会话、Mock 支付或员工页面到正式构建。

未采用的方案：

- 直接合并两个分支：会把首页、充值逻辑、构建配置和 API 冲突集中到一个合并中，难以确定每项行为来源。
- 重写生产分支历史后再合并：需要重建现有工作树并改写提交历史，增加回退和审计成本。

## 4. 环境与数据流

小程序不直接连接 PostgreSQL。环境由构建时注入的 API 地址和门店 ID 决定：

```text
小程序构建配置
  → HTTPS NestJS API
  → 对应环境的 PostgreSQL、Redis 和支付配置
```

### 4.1 测试验证构建

- 模式使用已经验证的微信测试模式。
- API 必须为 `https://judian.icu/test`。
- 门店必须为隔离测试门店。
- 数据继续写入测试 PostgreSQL 和测试 Redis。
- 真实微信登录和支付链路可以保留，但不得把测试数据描述为生产数据。

### 4.2 正式候选构建

- 模式必须为 `production-wechat`。
- API 必须精确为 `https://judian.icu`。
- 门店必须使用显式配置的正式门店 ID，不能回退到测试门店。
- 强制微信认证、真实手机号和真实微信支付。
- 禁止 `/test`、本地 HTTP、IP API、开发身份、虚拟手机号和 Mock。
- 正式 API 使用其既有生产 `DATABASE_URL`；不复制、导入、合并或重命名测试数据库。

## 5. 冲突处理与测试策略

### 5.1 测试版合并后

先运行：

```powershell
corepack pnpm miniapp:typecheck
corepack pnpm miniapp:test
corepack pnpm test
corepack pnpm typecheck
corepack pnpm build
```

然后显式生成测试环境小程序构建，检查：

- 编译配置只包含 `https://judian.icu/test`。
- 页面清单为新版顾客三页面结构。
- 不出现旧版门店状态、员工、店长或活动入口。
- 新版充值、月卡和历史记录相关测试通过。
- PC 交易记录、云同步、钱包和月卡一致性测试通过。

如果测试版阶段失败，停止生产移植；修复必须针对失败行为补充或使用已有回归测试，不能跳过测试直接切换正式环境。

### 5.2 生产提交移植

每个发生代码冲突的提交单独完成以下循环：

1. 先运行覆盖冲突行为的现有测试，确认当前新版基线为绿色。
2. 移植该生产行为及其测试。
3. 若现有测试不能表达冲突后的目标行为，先增加会失败的回归测试。
4. 实现最小冲突修正，使定向测试通过。
5. 再继续下一个生产提交。

生产配置、支付通知和部署脚本属于安全边界，不能通过“取一侧全部内容”解决冲突。

### 5.3 正式候选构建验收

完成生产提交后重新运行小程序、API、领域层、同步和工作区验证，并生成正式构建。自动检查：

- 产物 API 地址为 `https://judian.icu`，且不存在 `/test`。
- 产物门店 ID 与正式本地公共端点配置一致。
- `useMock=false`、`authMode=wechat`、`customerOnly=true`、`realWechatPayment=true`。
- 虚拟手机号关闭，开发身份为空。
- 正式构建没有员工、店长和内容管理页面。
- 正式充值配置不包含测试金额。
- 新版会员首页、明细页和“我的”页面仍存在。

## 6. 提交与回退边界

阶段性提交保持可审计：

1. 书面整合设计。
2. 已验收测试分支合并提交。
3. 测试环境合并冲突修复（仅在必要时）。
4. 按原顺序移植的生产提交及各自冲突修复。
5. 最终验证或文档更新提交（仅在文件实际变化时）。

若测试版整合失败，回退到测试版合并前的 `main` 提交，不进入生产阶段。若生产移植失败，保留已验证的测试版合并提交，并停止在失败的生产提交处排查；不得删除、覆盖或重写已经产生的正式充值、通知或钱包账本数据。

## 7. 完成标准

代码阶段完成必须同时满足：

1. `main` 包含完整的已验收测试分支历史和功能。
2. 测试环境构建明确访问 `/test`，新版页面与相关自动化验证通过。
3. `main` 包含正式构建、正式支付配置和部署防护能力。
4. 最终 `apps/miniapp/dist` 是 `production-wechat` 构建，只访问正式 API 和正式门店。
5. 工作区没有意外暂存或提交用户原有未跟踪文件。
6. 自动化和模拟器结果不会被描述为微信真机、真实支付、审核或正式发布通过。

后续仍需账号所有者完成体验版上传、真实微信登录与手机号授权、正式充值、商户平台对账、PC 同步核对、隐私检查、审核和发布。
