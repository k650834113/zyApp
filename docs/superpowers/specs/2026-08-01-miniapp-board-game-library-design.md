# 小程序桌游库、筛选与点赞设计

> 决策日期：2026-08-01
>
> 状态：视觉、交互与书面规格已确认；本轮实施边界已确认
>
> 适用范围：顾客微信小程序、公开桌游 API、微信轻量身份、云端桌游投影
>
> 视觉基线：沿用现有小程序的深森林绿、暖奶油白、圆角卡片和轻阴影

## 1. 目标

在现有正式小程序基础上新增顾客可用的“桌游库”，让到店前和到店后的顾客可以快速找到本店当前实际可玩的桌游。

完成后应满足：

1. 小程序底部导航调整为“首页 / 桌游库 / 明细 / 我的”。
2. 桌游库只展示当前门店已启用、公开、可玩、有可用数量且无缺件的桌游。
3. 顾客可以按名称、分类标签、适合人数、游玩时长和复杂度筛选。
4. 桌游卡片默认显示分类、人数、时长、复杂度和总赞数。
5. 点击卡片原地展开简介，再次点击收起，不进入独立详情页。
6. 所有微信用户都可以点赞或取消点赞，同一用户对同一桌游最多贡献一个赞。
7. 所有人都能看到每款桌游的当前总赞数。
8. “我的”页面在现有资料编辑结构中新增“我喜欢的”入口，进入后复用桌游库卡片。
9. 桌游复杂度使用人工录入的数字评分，例如 `2.3/5`，不再使用“轻度 / 中度 / 重度”。

## 2. 已确认的产品决策

### 2.1 导航与页面范围

采用四栏底部导航：

- **首页**：保留现有会员首页能力。
- **桌游库**：公开浏览、筛选、展开简介和点赞。
- **明细**：保留现有会员明细能力。
- **我的**：保留现有会员资料结构，新增“我喜欢的”入口。

新增两个页面：

- `桌游库`：一级底部导航页。
- `我喜欢的`：从“我的”进入的二级页面，使用返回导航，不再增加底部一级入口。

未采用的方案：

- 仅在首页放桌游库卡片：入口不够稳定，游客需要多一步才能找到。
- 在“我的”页面直接铺开收藏列表：会挤压当前头像、名称、账号资料和保存操作。
- 为每款桌游建立独立详情页：当前信息量不需要额外跳转，卡片原地展开更快。

### 2.2 公开范围

桌游库和“我喜欢的”都只返回当前门店实际可玩的桌游。服务端统一应用以下条件：

- 记录状态为启用。
- 当前门店允许顾客查看，不是私有桌游。
- 当前门店运营状态为可玩。
- 当前门店可用数量大于 0。
- 未标记缺件。

不满足条件的桌游直接从顾客列表隐藏，不显示“暂不可玩”或“已售罄”卡片。若用户曾点赞的桌游暂时不可玩，点赞记录保留，但该桌游不出现在“我喜欢的”中；恢复可玩后自动重新出现。

### 2.3 复杂度

现有 `light / medium / heavy` 难度枚举改为数字复杂度：

- 展示格式固定为一位小数，例如 `2.3/5`。
- 合法范围为 `0.0–5.0`，按 `0.1` 递增。
- 复杂度由店方参考 BGG 或集石后人工填写，顾客端不提供编辑能力。
- 上线前，所有公开且可玩的桌游必须补齐复杂度；未补齐的记录不进入正式发布验收数据集。
- 不在顾客端显示外部来源链接，不自动抓取 BGG 或集石数据。

为了平滑迁移，数据库新增数值字段 `complexity_rating`，不直接把旧枚举列改写为数字。旧枚举在兼容期保留，但新小程序和新接口只读取数值复杂度。确认所有桌游已补齐且旧客户端退场后，再单独清理旧字段。

### 2.4 点赞身份

所有人都能直接浏览。首次点赞时，如当前没有可识别的微信会话，小程序先通过 `wx.login` 完成轻量微信身份识别，不要求填写会员名称、手机号或会员资料。

身份规则：

- 服务端将微信身份映射为内部不透明的 `viewerId`。
- 点赞记录只保存内部 `viewerId`，不向客户端返回 OpenID 或其他微信标识。
- 同一微信用户注册或绑定正式会员后继续使用同一 `viewerId`，原点赞不会丢失。
- “我的 → 我喜欢的”对轻量微信用户和正式会员都可用。
- 浏览不强制登录；点赞、取消点赞和查看“我喜欢的”需要有效微信会话。

不采用纯本地收藏。纯本地状态无法提供可信总赞数，也不能跨设备恢复或可靠取消点赞。

## 3. 桌游库交互设计

### 3.1 页面结构

桌游库从上到下包含：

1. 页面标题“桌游库”。
2. 搜索框，支持名称和分类标签关键词。
3. 快捷筛选条：“分类 / 人数 / 时长 / 复杂度”。
4. 当前已选条件标签，可单项移除。
5. 结果数量和“推荐优先”排序说明。
6. 桌游卡片列表。
7. 四栏底部导航。

首次进入默认不设置筛选条件，按“店长推荐优先，其次名称”排序。搜索或筛选条件变化后，列表显示明确的加载状态；保留上一批结果直到新结果成功返回，避免页面闪空。

### 3.2 筛选面板

点击任一筛选按钮打开底部面板。面板包含：

- **分类**：多选标签，显示复选状态。
- **适合人数**：双端拖拉条，例如 `3–6 人`。
- **游玩时长**：双端拖拉条，例如 `30–120 分钟`。
- **复杂度**：双端拖拉条，例如 `1.0–3.0 / 5`。
- **清空**：恢复全部条件。
- **查看 N 款桌游**：应用条件并显示服务端返回的当前预计数量。

筛选语义固定为：

- 多个分类标签使用“同时包含”语义；选择“德式 + 策略”时，结果必须同时拥有两个标签。
- 人数范围表示桌游必须覆盖整个选择范围；选择 `3–6 人` 时，桌游应满足 `minPlayers <= 3` 且 `maxPlayers >= 6`。
- 时长范围与桌游标称时长范围有交集即可匹配；缺少时长数据的桌游在设置时长筛选后不匹配。
- 复杂度数值必须落在所选闭区间内；缺少复杂度数据的桌游在设置复杂度筛选后不匹配。
- 名称搜索与分类、人数、时长和复杂度条件之间使用“同时满足”语义。

人数、时长和复杂度拖拉条必须同时提供可读数值，不能只依赖滑块位置。两个滑块端点不能交叉；拖动到相同值时表示精确筛选。

### 3.3 卡片信息层级

每张桌游卡片默认包含：

- 桌游封面；没有图片时使用统一占位图，不显示损坏图片框。
- 桌游名称。
- 右上角爱心与总赞数。
- 单独一行分类标签，可换行容纳多个标签，例如“德式 / 策略 / 竞争”。
- 下一行并列显示“人数 · 时长 · 复杂度”，例如 `2–4 人 · 30 分钟 · 复杂度 2.3/5`。
- “点击展开简介”提示。

人数、时长和复杂度必须在同一行。窄屏不足时允许整体换到下一行，但三项的顺序和分隔符保持一致；分类标签不与这三项混排。

### 3.4 展开与收起

- 点击卡片非爱心区域，卡片在原位置展开简介。
- 再次点击同一卡片收起。
- 爱心是独立点击区域，点击爱心不得触发卡片展开或收起。
- 同一时间允许多个卡片保持展开，避免用户展开新卡片时丢失之前的比较上下文。
- 展开内容只显示顾客简介，不显示内部备注、寄存人、缺件明细或运营字段。

### 3.5 点赞与取消点赞

默认状态使用空心 `♡`，已点赞状态使用实心 `♥`。两种状态旁边都显示当前总赞数。

交互顺序：

1. 用户点击爱心。
2. 客户端立即更新爱心和数字，提供快速反馈。
3. 若没有微信会话，先完成轻量微信身份识别。
4. 客户端提交明确的目标状态 `liked: true` 或 `liked: false`，而不是提交非幂等的“切换”命令。
5. 服务端确认后保留新状态；失败时恢复原状态并提示可重试。

同一用户对同一桌游最多一条有效点赞。重复请求、网络重试和多设备同时操作都不得重复增加总赞数。

## 4. “我的”与“我喜欢的”

### 4.1 “我的”页面

保留当前页面的：

- 头像选择。
- 会员名称。
- 绑定手机号。
- 会员等级。
- 保存资料按钮。

在账号资料卡和保存资料按钮之间新增一条独立选项：

- 左侧爱心图标。
- 标题“我喜欢的”。
- 副标题“已收藏 N 款桌游”。
- 右侧进入箭头。

点击该选项进入独立“我喜欢的”页面。轻量微信用户尚未注册会员时，仍可看到该入口和收藏数量；会员资料区域按现有游客状态显示登录或完善资料引导。

### 4.2 “我喜欢的”页面

页面复用桌游库的卡片组件和相同字段：

- 分类单独一行。
- 人数、时长、复杂度同一行。
- 简介原地展开和收起。
- 爱心状态和总赞数。

取消点赞后，该卡片从“我喜欢的”列表移除，同时更新页面数量。返回桌游库后状态保持一致。

空状态文案为“还没有喜欢的桌游，去桌游库逛逛吧”，并提供返回桌游库的按钮。

## 5. 数据与接口设计

### 5.1 公开桌游 DTO

公开桌游摘要在现有字段基础上调整为：

- `id`
- `name`
- `introduction`
- `categories: string[]`
- `minPlayers`
- `maxPlayers`
- `minMinutes`
- `maxMinutes`
- `complexityRating: number | null`
- `imageUrl`
- `customerNote`
- `likeCount: number`
- `likedByViewer: boolean`

不再向新小程序 DTO 返回 `difficulty: light | medium | heavy`。`complexityRating` 在本轮真实数据尚未完成补录时允许为 `null`，卡片显示“复杂度待补充”，且设置复杂度筛选后不匹配。`likedByViewer` 在匿名浏览且没有微信会话时返回 `false`，`likeCount` 始终返回真实聚合值。

### 5.2 点赞存储

新增云端点赞关系，至少包含：

- 点赞 ID。
- 租户 ID。
- 门店 ID。
- 桌游 ID。
- 内部 `viewerId`。
- 创建时间。

唯一约束为 `(tenant_id, store_id, board_game_id, viewer_id)`。创建点赞使用冲突忽略或等价幂等写入；取消点赞只删除命中的关系。总赞数初版通过关系表聚合，不新增可漂移的独立计数器。后续只有在真实数据证明聚合性能不足时才增加可校验缓存。

桌游主档仍是租户级共享，但点赞按当前门店统计。不同门店即使引用同一桌游主档，也分别维护点赞关系和总赞数。“我喜欢的”同样按当前门店查询，避免切换门店后混入另一门店的收藏。门店是否公开、可玩、数量和缺件状态继续按当前门店配置判断。

### 5.3 API 边界

公开列表接口支持以下可选查询条件：

- `query`
- `categories[]`
- `minPlayers`
- `maxPlayers`
- `minMinutes`
- `maxMinutes`
- `minComplexity`
- `maxComplexity`

服务端负责应用公开范围和筛选语义，客户端不得先下载全库再自行判断可见性。

新增轻量微信身份下的接口能力：

- 设置某桌游点赞状态：输入桌游 ID、目标 `liked` 状态和幂等请求 ID。
- 查询当前用户喜欢的桌游：复用公开桌游摘要并应用当前门店可玩条件。

点赞写入只接受服务端验证过的微信会话。客户端不能提交 `viewerId`、OpenID 或总赞数。服务端返回权威的 `likedByViewer` 和 `likeCount`。

### 5.4 客户端与数据库边界

- 小程序继续只调用 HTTPS NestJS API，不直接连接 PC SQLite 或 PostgreSQL。
- PC 仍是桌游资料和复杂度的主要维护入口。
- 桌游复杂度随现有桌游主档同步到云端。
- 点赞是云端顾客行为，不下行到 PC SQLite，也不进入离线 outbox。
- 点赞不是资金或经营状态操作，不写钱包、订单或财务账本。

## 6. 错误与边界状态

- 列表加载失败：保留已显示内容并提供重试，不伪造空列表。
- 筛选无结果：显示“没有找到符合条件的桌游”，保留筛选条件并提供清空入口。
- 点赞身份获取失败：恢复爱心和数字，提示重新尝试，不强制进入会员注册。
- 点赞请求超时：使用同一请求 ID 查询或重试目标状态，不重复增加赞数。
- 多设备同时点赞：唯一约束保证每个用户最多贡献一个赞，响应返回最新总数。
- 桌游在浏览后变为不可玩：刷新或后续请求时从桌游库和“我喜欢的”移除。
- 图片加载失败：显示统一占位图，文本、筛选和点赞仍可使用。
- “我喜欢的”取消最后一款：进入空状态，不返回上一页。
- 复杂度录入超出范围或超过一位小数：PC 和 API 均拒绝保存。

## 7. 测试与验收

### 7.1 自动化测试

至少覆盖：

- 公开列表只返回启用、公开、可玩、数量大于 0 且无缺件的桌游。
- 门店配置覆盖共享桌游主档时按当前门店状态过滤。
- 分类多选使用同时包含语义。
- 人数范围要求桌游覆盖完整选择范围。
- 时长范围使用区间相交语义。
- 复杂度使用闭区间和一位小数校验。
- 搜索与其他筛选条件组合正确。
- 卡片展开不触发点赞，点赞不触发展开。
- 首次点赞创建轻量微信身份但不创建虚假会员资料。
- 同一用户重复点赞、重试点赞和并发点赞只贡献一个赞。
- 取消点赞只减少一次并返回权威总数。
- 匿名列表能看到总赞数但 `likedByViewer` 为 `false`。
- “我喜欢的”只返回当前用户点赞且当前门店实际可玩的桌游。
- 注册会员前后的点赞仍属于同一微信身份。
- 复杂度旧枚举兼容期不泄漏到新 DTO。
- Mock、体验版和正式版构建均包含批准的新页面；正式版仍拒绝开发身份和 Mock 数据。

### 7.2 人工验收

1. 未登录进入小程序，确认底部导航为“首页 / 桌游库 / 明细 / 我的”。
2. 打开桌游库，确认不可玩、私有、无数量和缺件桌游均不显示。
3. 使用名称搜索和多个分类标签筛选。
4. 拖动人数到 `3–6 人`，确认只显示覆盖完整人数范围的桌游。
5. 拖动时长和复杂度范围，确认数值实时更新且结果正确。
6. 检查“璀璨宝石”等多标签卡片，确认分类独占一行，人数、时长、复杂度同一行。
7. 点击卡片展开简介，再次点击收起。
8. 点击爱心，确认不展开卡片，首次操作只完成轻量微信身份识别，不要求填写会员资料。
9. 退出并重新进入，确认爱心状态保持，总赞数只增加一次。
10. 再次点击爱心取消，确认总赞数减少一次。
11. 在另一微信账号查看同一桌游，确认看到一致的总赞数但未自动点赞。
12. 在“我的”现有资料页面看到“我喜欢的”入口。
13. 进入“我喜欢的”，确认复用同一套卡片并可展开简介。
14. 在“我喜欢的”取消点赞，确认卡片移除，返回桌游库后状态一致。
15. 将已点赞桌游改为不可玩，刷新后确认两个顾客页面均隐藏；恢复可玩后重新出现。

## 8. 实施边界与顺序

### 8.1 本轮交付

本轮只完成小程序页面、公开桌游接口和点赞闭环，具体包括：

1. 共享合同与云端 PostgreSQL 增加可空数字复杂度字段，并新增点赞关系表。点赞关系表属于点赞接口可跨设备、可统计总数所必需的最小云端持久化，不进入 PC SQLite 和离线同步。
2. 云端公开列表增加实际可玩过滤、服务端筛选、总赞数和查看者状态。
3. 复用现有微信会话建立轻量查看者身份，并提供幂等设置点赞状态与“我喜欢的”查询接口。
4. 小程序增加四栏导航、桌游库、筛选面板、可展开卡片、“我的”入口和独立“我喜欢的”页面。
5. Mock 数据为展示用桌游补齐数字复杂度，以便本轮完成页面和交互验收。
6. 完成合同、API、小程序单元测试、Mock 构建和可用环境下的模拟器验收。

本轮复杂度接口字段允许为空。未设置复杂度时，卡片显示“复杂度待补充”；只有用户启用复杂度筛选时，该桌游不匹配。正式生产数据发布前，仍须按第 2.3 节补齐所有公开且可玩桌游的复杂度。

- PC 到云端的桌游主档同步协议及复杂度同步。
- 现有真实桌游数据的复杂度查询、人工录入与批量补齐。
- 依赖真实复杂度数据的正式生产发布与真机最终验收。

后续推荐顺序为：

1. PC 桌游资料编辑改为数字复杂度。
2. PC SQLite 与云端同步合同增加数字复杂度。
3. 补齐现有公开桌游数据并完成迁移核对。
4. 使用真实生产数据完成体验版、真机和正式发布验收。

### 8.3 产品范围外

本设计明确不包含：

- 顾客评论、文字评价或星级评分。
- 自动抓取 BGG 或集石数据。
- 桌游预约、占用、借出或桌台管理。
- 对外展示精确库存数量、缺件详情或寄存人信息。
- 独立 Web 管理后台。
