# 小程序正式充值预估与生产库验收设计

> 决策日期：2026-07-27
>
> 状态：已确认，等待书面规格复核
>
> 适用范围：微信小程序会员端、正式 NestJS API、正式 PostgreSQL 数据库、微信支付 API v3

## 1. 目标

本轮交付用于正式版本验收的小程序构建和服务端配置。小程序必须使用正式数据库、正式门店、正式充赠档位、真实微信登录、真实手机号授权和真实微信支付，不再保留隔离测试库、0.01 元测试档位、虚拟手机号、开发会话或 Mock 支付入口。

同时改进充值选择体验：

1. 每个正式充值档位实时显示本次充值的预计赠送金额和预计到账金额。
2. “实际赠送以创建充值订单时的规则为准”旁显示可点击的小感叹号。
3. 点击感叹号后展示当前正式门店实际生效的充赠规则和计算说明。
4. 页面预估和服务端下单使用同一组规则；最终财务结果仍以创建订单时由服务端计算并冻结的规则快照为准。

## 2. 已确认的产品与环境决策

### 2.1 正式版本边界

- 新增独立的 `production-wechat` 小程序构建模式。
- 正式构建只允许访问 `https://judian.icu`，不得访问 `/test`、IP 测试入口或本地 HTTP API。
- 正式构建只包含顾客页面，不包含店员、店长和内容管理页面。
- 正式构建强制使用微信认证和真实微信支付。
- 正式构建禁止虚拟手机号、开发身份、Mock 客户端和 Mock 结算。
- 正式 API 使用生产 PostgreSQL 数据库和生产 Redis。
- 正式充值档位为当前业务配置中的正式档位；不显示或接受 0.01 元测试充值。

### 2.2 充赠规则口径

充赠规则以正式门店当前生效的业务模板为第一来源，门店覆盖优先于商户模板；只有不存在有效模板时，才使用当前有效的兼容充赠档位投影。

计算继续遵守既有业务规则：

- 低于最高档时，只应用一个符合条件的最高档位。
- 达到或超过最高档时，最高档可重复计算。
- 重复最高档后的余数至多再应用一个符合条件的档位。
- 例如默认规则下，999 元赠送 50 元，而不是 70 元。
- 金额始终使用整数分。

本轮不修改充赠算法，只修正页面数据来源和展示方式。

## 3. 方案选择

采用“服务端下发当前规则、客户端实时预估、创建订单时服务端重新计算并冻结快照”的方案。

未采用的方案：

- 继续从公开活动推算赠送：公开宣传活动与实际启用的充赠规则是两个独立状态，可能导致页面预估和财务结算不一致。
- 点击档位时创建预览订单：虽然可以获得精确快照，但会产生大量无支付意图的待支付订单和微信预支付单。

推荐方案兼顾即时反馈、规则权威性和财务可审计性。客户端预估只用于展示，服务端仍是唯一财务决策边界。

## 4. 接口与数据流

### 4.1 充值配置接口

扩展现有 `GET /v1/member/recharge-configuration` 响应，增加当前适用的充赠档位：

```ts
type MemberRechargeConfiguration = {
  providerMode: 'mock' | 'wechat'
  testAmountFen: number | null
  giftTiers: Array<{
    principalFen: number
    giftFen: number
  }>
}
```

正式环境响应必须满足：

- `providerMode` 为 `wechat`。
- `testAmountFen` 为 `null`。
- `giftTiers` 来自当前会员所属租户和当前正式门店实际生效的规则。
- 档位按本金金额升序返回。
- 无效、负数、重复本金档位或超出安全整数范围的数据不得返回给客户端。

服务端提取一个可复用的“解析当前充赠规则”内部边界，配置查询和充值订单创建共同调用，避免两套 SQL 或模板合并逻辑逐渐分叉。

### 4.2 页面预估

小程序获得配置后，用现有业务算法计算固定正式充值档位的预计赠送：

```text
当前规则
   ↓
充值档位本金
   ↓
预计赠送
   ↓
预计到账 = 本金 + 预计赠送
```

客户端计算仅影响显示，不参与订单入账。用户点击充值档位后，客户端只提交本金金额和幂等请求 ID。

### 4.3 创建订单与冻结快照

服务端创建订单时：

1. 在当前租户、门店和会员上下文中重新读取适用规则。
2. 使用领域层充赠算法重新计算赠送金额。
3. 将规则档位和分配结果写入 `gift_rule_snapshot_json`。
4. 创建真实微信预支付单。
5. 只有可信微信支付通知或主动查单结果可以结算钱包。

如果用户停留页面期间规则发生变化，充值订单使用创建订单时的新规则；订单卡片展示服务端返回的实际赠送金额。小字已明确该边界。

## 5. 小程序交互设计

### 5.1 正式充值档位

每张充值档位卡显示：

- 支付金额。
- `预计赠送 ¥X`；无赠送时显示“预计赠送 ¥0”。
- `预计到账 ¥X`。

不得再使用“快捷充值”代替零赠送信息，以免用户无法判断是否已完成计算。

### 5.2 规则说明入口

充值档位区域下方显示：

```text
实际赠送以创建充值订单时的规则为准  ⓘ
```

感叹号使用按钮语义和足够的点击区域，不仅依赖图标本身。点击后调用 `wx.showModal` 展示：

- 标题：“当前充赠规则”。
- 当前档位列表，例如“充 ¥300 赠 ¥20”。
- 最高档重复计算说明。
- 余数至多匹配一个档位的说明。
- “最终赠送以创建订单时服务端返回结果为准”。

规则为空时不伪造默认规则。页面显示“当前暂无赠送规则”，所有档位预计赠送为 ¥0，订单仍由服务端最终确认。

### 5.3 充值订单展示

创建订单后继续展示：

- 支付金额。
- 服务端返回的赠送金额。
- 总到账金额。
- 支付状态。

订单卡片中的赠送值是创建订单时的实际快照，不再标为客户端预估。

## 6. 正式构建与部署设计

### 6.1 小程序构建防误配

新增 `production-wechat` 模式并设置以下硬性校验：

- API 地址必须精确为 `https://judian.icu`。
- 认证模式必须为 `wechat`。
- 虚拟手机号必须关闭。
- `customerOnly` 和 `realWechatPayment` 必须为 `true`。
- 正式门店 ID 必须显式配置，不能回退使用测试门店 ID。
- 正式构建不能从 `miniappTestApiBaseUrl` 或 `miniappTestStoreId` 读取默认值。

本地公共端点配置增加独立的正式 API 地址和正式门店 ID 字段。该文件继续被 Git 忽略；它只包含可公开的端点和标识，不包含数据库、AppSecret 或支付密钥。

### 6.2 正式 API 微信支付

正式 API 从当前 `disabled` 切换为 `wechat`，并使用正式环境变量和只读密钥挂载：

- 正式微信支付通知地址为 `https://judian.icu/v1/payments/wechat/recharge/notify`。
- 正式商户订单前缀与测试订单前缀不同，避免运营对账混淆。
- 正式环境不设置 `WECHAT_PAYMENT_TEST_AMOUNT_FEN`。
- 正式环境不得设置测试虚拟手机号。
- AppSecret、商户私钥、微信支付公钥和 API v3 密钥只保存在服务器受限环境文件或只读密钥目录，不进入代码、构建产物、命令输出和日志。

API 配置校验增加正式通知地址约束，防止正式订单把支付通知发往 `/test`。

### 6.3 数据切换

“切换正式库”通过正式小程序访问正式 API 实现，不复制、合并或重命名测试数据库。

- 测试数据库保留原验收数据，不导入生产库。
- 正式小程序使用正式门店 ID。
- 正式 API 继续使用现有生产 `DATABASE_URL`。
- 上线前只读核对正式门店、租户、会员和当前充赠模板；不运行测试库种子脚本。
- 若正式门店尚无有效充赠模板，停止发布并先由现有正式 PC/同步流程补齐规则，不在服务器上手工伪造业务数据。

## 7. 发布安全、备份与回退

部署前：

1. 运行正式 PostgreSQL 自定义格式备份并生成 SHA-256。
2. 核对备份文件非空、校验文件存在。
3. 只读核对正式数据库迁移版本、正式门店 ID、当前充赠规则和微信支付所需配置是否齐全。
4. 构建并自动验证 `production-wechat` 产物中不存在测试端点、0.01 元档位和员工路由。

部署时：

1. 先部署支持规则接口和正式微信支付的 API。
2. 等待正式健康检查通过。
3. 验证正式充值配置接口的认证和环境边界。
4. 再生成供微信开发者工具上传的正式小程序构建。

回退策略：

- API 部署失败时恢复上一版服务镜像或代码，正式数据库保留迁移兼容状态。
- 未发起正式充值前，可关闭正式微信支付并回退小程序体验版。
- 已创建或已结算的正式充值订单不得删除或改写；回退后仍须保留订单、通知收件箱和钱包账本。
- 已产生真实资金的订单只能通过后续正式退款/冲正流程处理，不能恢复数据库备份覆盖。

## 8. 错误处理

- 规则接口失败：不显示未经确认的预计赠送，不允许以旧活动数据替代；提示用户稍后重试。
- 规则为空：显示预计赠送 ¥0 和“当前暂无赠送规则”。
- 页面预估与订单结果不同：订单卡片使用服务端结果，支付前展示最新实际赠送；不修改订单快照。
- 正式支付配置缺失：API 启动失败或充值接口明确不可用，不回退到 Mock。
- 正式门店 ID 缺失或误用测试 ID：构建失败。
- 支付通知误配为测试路径：API 配置校验失败。
- 微信重复通知或客户端重复查询：继续使用现有幂等结算边界，只入账一次。
- 网络结果不明确：查询原订单，不重复创建订单。

## 9. 自动化测试

至少覆盖：

- 配置接口返回与创建订单相同来源的当前有效档位。
- 商户模板和门店覆盖合并结果正确。
- 兼容档位投影回退正确。
- 重复或无效档位被拒绝或规范化。
- 100、300、500、1000 元档位的预计赠送符合服务端领域算法。
- 999 元只赠送 50 元。
- 1300 元按默认规则赠送 220 元。
- 规则为空时预计赠送为 0。
- 规则弹窗文本来自接口返回规则。
- 创建订单后使用服务端赠送结果覆盖页面预估语义。
- `production-wechat` 只接受 `https://judian.icu` 和显式正式门店 ID。
- 正式构建拒绝 `/test`、IP 地址、开发认证和虚拟手机号。
- 正式 API 拒绝测试通知 URL 和测试充值金额。
- 正式环境支付配置缺失时不得启动为 Mock。
- 正式小程序构建中没有 0.01 元档位、测试警告和员工页面。
- 原 Mock、开发和隔离测试构建继续通过既有测试。

## 10. 自动与人工验收

自动验收：

1. 运行小程序类型检查、完整测试和 Mock 构建。
2. 运行 API 配置、充值服务、微信支付通知和领域层定向测试。
3. 运行完整工作区类型检查和相关服务构建。
4. 生成 `production-wechat` 构建，检查编译配置、正式端点和页面清单。
5. 部署前后验证正式 API 健康状态和数据库备份。
6. 使用微信开发者工具模拟器检查充值档位、预计赠送和规则弹窗；模拟器结果不代表真实支付通过。

账号所有者人工验收：

1. 上传正式构建为体验版。
2. 使用真实微信完成登录和手机号授权。
3. 核对会员、余额和历史记录来自正式库。
4. 核对每个正式档位的预计赠送和规则弹窗。
5. 选择一个正式档位并确认微信支付页金额正确。
6. 完成真实支付。
7. 在商户平台核对交易、商户订单号和正式通知。
8. 在小程序核对本金、赠送金额和总余额只增加一次。
9. 在 PC 端同步并核对正式充值单、钱包账本和会员余额。

微信体验版上传、真机授权、真实付款、商户平台对账、隐私检查、审核和发布必须由账号所有者参与。自动化或模拟器结果不能替代这些步骤。

## 11. 不在本轮范围

- 继续保留或新增 0.01 元正式库测试档位。
- 把测试数据库数据导入正式数据库。
- 修改既有充赠算法或默认金额。
- 微信退款和充值撤销功能。
- 店员、店长或移动收银页面重新进入顾客正式构建。
- 独立 Web 管理后台。
