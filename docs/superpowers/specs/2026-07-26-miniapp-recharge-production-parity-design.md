# 小程序体验版与正式版充值功能一致性设计

> 日期：2026-07-26  
> 目标分支：`codex/member-recharge-pc-transactions`

## 已确认目标

体验版必须完整测试将来正式投入生产的小程序能力：

- 体验版和正式版都显示快捷充值与自定义充值；
- 快捷金额固定为 100、300、500、1000 元；
- 自定义金额最低 0.01 元，最多两位小数；
- 用户自行输入小额金额完成真实微信支付测试；
- 不再存在点击充值后被测试环境强制改为 0.01 元的专用流程；
- 两套版本使用相同页面、相同接口、相同金额校验、相同赠送规则和相同支付状态处理；
- 体验与生产只隔离 API 地址、门店、数据库、Redis、头像卷、订单前缀及微信支付回调地址；
- 体验通过前继续保持当前分支，不合并、不推送 Git。

## 方案比较

### 方案 A：客户端固定快捷金额，自定义金额走统一订单接口（采用）

小程序固定展示 100、300、500、1000 元，并提供自定义金额输入框。所有金额统一转换为整数分后调用现有
`POST /v1/member/recharge-orders`。

优点：

- 体验版与正式版页面和接口完全一致；
- 改动集中，不引入新的门店配置接口；
- 0.01 元和正式充值使用同一支付链路；
- 现有服务端赠送档位继续决定实际赠送金额。

代价：若以后要让不同门店配置不同快捷按钮，需要再把快捷金额移入门店配置。

### 方案 B：服务端下发快捷金额

扩展充值配置接口，让每个门店返回快捷金额列表。

优点：未来可按门店配置。  
代价：当前需求已确认固定金额，会额外扩大契约、数据库配置和管理界面范围。

### 方案 C：保留测试专用 0.01 元入口

继续由测试 API 返回固定金额，正式版使用普通金额。

优点：改动最少。  
缺点：体验版与正式版行为不同，无法达到本次验收目标，因此不采用。

## 小程序交互

会员首页余额卡下方显示充值卡片：

1. 展示 100、300、500、1000 元四个快捷按钮；
2. 展示“自定义金额（元）”输入框；
3. 点击快捷金额会选中该金额并清空自定义输入；
4. 输入自定义金额会取消快捷金额选中状态；
5. 点击“微信支付”后校验并创建充值订单；
6. 金额必须为 0.01–1,000,000.00 元，最多两位小数；
7. 支付处理中禁用重复提交；
8. 取消、待确认、到账和失败继续使用现有状态轮询与提示。

金额转换使用字符串解析，不通过浮点乘法直接生成财务金额。例如：

- `0.01` 转为 1 分；
- `100` 和 `100.00` 转为 10000 分；
- `1.001`、`0`、负数、非数字和超上限输入均被拒绝。

## API 与财务规则

- 保留现有充值配置、创建订单、查询订单和微信回调路由。
- `MemberRechargeConfiguration` 只表达支付提供方模式，不再向客户端下发
  `testAmountFen`。
- 创建订单继续接受 1–100000000 分。
- 删除“只有测试环境明确开启时才允许 1 分”的特殊限制；体验和生产都允许
  1 分订单。
- 1 分充值自然不命中赠送档位，到账本金 1 分、赠送 0 分。
- 其他金额继续按当前门店生效的赠送档位计算，创建订单时冻结规则快照。
- 充值、赠送、支付、钱包账本、审计和幂等规则不变。

## 构建与部署一致性

- `production-test-wechat` 和 `production-wechat` 都启用真实充值界面。
- 两个构建都禁止 Mock 支付、虚拟手机号和开发会话。
- 构建测试会把 API 地址和门店 ID 归一化后比较两套客户版配置，除环境标识外必须一致。
- 测试 API 使用测试 PostgreSQL、Redis、头像卷、`/test` 回调和测试订单前缀。
- 生产 API 使用生产 PostgreSQL、Redis、头像卷、根路径回调和生产订单前缀。
- 生产 Compose 补齐真实微信支付参数和只读密钥挂载，但支付模式仍由明确的生产环境开关控制；
  本次不得重建或重启生产 API。
- 测试 Compose 不再设置 `WECHAT_PAYMENT_TEST_AMOUNT_FEN=1`。

## 错误与安全

- 客户端在创建订单前显示可理解的金额错误，不向服务端提交非法金额。
- 服务端仍做最终整数分范围校验，客户端校验不能替代服务端校验。
- 每次点击支付生成新的请求号；不确定结果时继续按原订单查询，不能重复记账。
- 微信支付密钥、证书和 APIv3 密钥只挂载到服务端，不进入小程序包、Git 或日志。
- 年龄资格为 `recharge_disabled`、会员停用或支付服务不可用时继续拒绝充值。

## 自动化验证

- 金额解析覆盖 0.01 元、快捷金额、两位小数、非法字符、三位小数、零、负数和超上限。
- 体验版和正式版构建配置都启用真实充值且只在 API/门店环境上不同。
- API 在没有测试金额开关时仍接受 1 分订单，并确认赠送为 0。
- 既有幂等、赠送档位、支付回调和钱包到账测试继续通过。
- 小程序类型检查、测试和两种客户版构建通过。
- 测试 API 部署后，生产容器 ID 保持不变。

## 真机验收

账号所有者在体验版完成：

1. 依次选中四个快捷金额，确认显示金额正确，可在调起支付后取消；
2. 输入 0.01 元，完成一次真实支付；
3. 确认钱包本金只增加 1 分、赠送为 0；
4. 输入一个能命中赠送档位的自定义金额，调起支付后取消，不产生到账；
5. 检查取消、待确认和成功状态没有重复订单；
6. 确认线上现有小程序和生产数据不受测试部署影响。

体验验收通过后，再合并分支并推送 Git；正式发布时使用同一代码构建
`production-wechat`，切换到生产 API 与生产门店。
