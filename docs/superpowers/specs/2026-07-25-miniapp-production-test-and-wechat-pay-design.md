# 小程序生产化测试与微信支付 API v3 接入设计

> 决策日期：2026-07-25
>
> 状态：已确认，等待书面规格复核
>
> 范围：游客、会员登录、余额、月卡、历史记录、在线充值
>
> 暂不包含：店员、店长、移动收银、支付退款和正式库切换

## 1. 目标与验收结果

本次交付一个可在微信开发者工具和真机上测试的原生微信小程序初版。除数据库使用隔离测试库，以及提供一个明确标注的 0.01 元实付测试档位外，登录、网络、HTTPS、微信支付和服务端结算均按生产方式运行。

交付完成必须同时满足：

1. PC 继续通过 `https://124.220.69.209` 使用现有生产和测试通道。
2. 小程序只通过 `https://judian.icu/test` 访问测试 API。
3. 测试 API 使用隔离 PostgreSQL 测试库，不写入生产数据库。
4. 小程序使用真实 `wx.login`、真实手机号授权和真实微信支付，不存在 Mock 登录、虚拟手机号或 Mock 结算入口。
5. 游客可查看公开首页；会员可登录并查看余额、月卡、消费记录、充值记录和月卡历史。
6. 会员可发起一笔真实的 0.01 元 JSAPI 支付。支付成功后，测试钱包本金只增加 1 分，且不产生赠送金额和高级会员来源。
7. 微信重复通知、客户端重复查询或网络重试均不得重复入账。
8. 店员、店长和内容管理入口不向顾客展示，也不进入本次验收范围。

真实支付测试产生真实资金交易，不是微信支付沙箱。首轮只使用 0.01 元档位。

## 2. 方案选择

采用后端直接接入微信支付 API v3 的方案。NestJS API 使用 Node.js 原生 `crypto` 和现有 HTTP 能力完成请求签名、应答验签、通知验签与通知资源解密，不引入第三方微信支付 SDK。

未采用的方案：

- 社区 SDK：开发代码可能更少，但增加依赖维护、供应链和微信支付规则升级风险。
- 第三方支付网关：引入额外费用、数据边界和供应商依赖，不符合当前单商户、单小程序的规模。

直接接入保留现有支付适配器边界。Mock 适配器继续用于自动化测试，真实适配器只在显式的微信支付模式下启用。

## 3. 环境和 HTTPS 架构

### 3.1 双入口

Caddy 同时托管两个 TLS 入口：

- `https://124.220.69.209`：保留 PC 当前访问方式和现有 IP 证书。
- `https://judian.icu`：使用已签发的域名证书，供小程序使用。

两个入口使用相同的路由规则：

- `/test/*` 转发到测试 API，并移除 `/test` 前缀。
- 其他 API 路径继续转发到生产 API。

Caddy 配置显式保留 IP 站点和域名站点；默认 TLS SNI 仍指向 IP 站点，以兼容现有 PC 连接。部署只重建 Caddy 网关，不重建数据库、API 或 worker 容器。

部署后必须分别检查以下四个地址的 TLS 和健康状态：

- IP 生产健康地址
- IP 测试健康地址
- 域名生产健康地址
- 域名测试健康地址

### 3.2 微信公众平台配置

在微信公众平台“小程序后台 → 开发管理 → 开发设置 → 服务器域名”中配置：

- `request 合法域名`：`https://judian.icu`

当前初版不使用 WebSocket、UDP、TCP、DNS 预解析，也不直接使用 `wx.uploadFile` 或 `wx.downloadFile`，对应域名先留空。以后实际启用这些 API 时再增加相应域名。

微信支付通知地址不是在“服务器域名”页面填写，而是后端创建每笔支付订单时提交：

`https://judian.icu/test/v1/payments/wechat/recharge/notify`

### 3.3 测试环境隔离

新增一个明确的生产化测试构建模式。该模式固定满足：

- API 地址必须是 HTTPS，且为 `https://judian.icu/test`。
- 使用正式小程序 AppID。
- 微信认证模式为真实微信认证。
- 虚拟手机号功能关闭。
- 开发者测试主体和 Mock 客户端关闭。
- 目标门店固定为已确认的测试门店。
- 支付模式为真实微信支付。
- 数据库固定为测试数据库。

构建脚本在缺少以上条件或检测到 HTTP、Mock、虚拟手机号时直接失败，避免生成“看似生产、实际仍是 Mock”的包。

生产 API 的支付模式保持关闭。本次只给测试 API 启用真实支付，以防误写生产钱包。

## 4. 小程序范围与交互

### 4.1 页面范围

初版保留：

- 首页和公开活动信息
- 微信登录及手机号授权
- 会员资料
- 钱包本金、赠送余额与总余额
- 月卡状态
- 最近消费记录
- 充值记录
- 月卡事件历史
- 在线充值

店员、店长和内容管理代码可以继续留在仓库中，但生产化测试构建不展示入口、不自动跳转到这些页面，也不把其能力作为本次发布条件。后续恢复时通过显式能力配置开启，不复制第二套页面。

### 4.2 充值档位

正常充值档位继续遵循服务端当时生效的充值赠送规则，金额统一以整数分表示。订单创建时冻结本金、赠送金额和会员权益来源快照，后续活动变化不能修改既有订单。

生产化测试模式额外显示：

- `0.01 元真实支付测试`
- 本金 1 分
- 赠送 0 分
- 不产生高级会员资格
- 页面明确提示“真实扣款，资金进入商户号；余额写入测试库”

该档位由测试 API 的显式配置提供，服务端同时校验，不能仅依靠前端按钮控制。正式环境未启用该配置时，不能创建 1 分测试订单。

## 5. 微信支付数据流

### 5.1 创建订单

1. 已登录会员提交稳定的请求 ID、充值金额和当前门店上下文。
2. API 校验会员身份、年龄充值资格、测试档位开关、门店和租户范围。
3. API 在 PostgreSQL 事务中创建 `creating` 状态的充值订单，并冻结赠送和会员权益快照。
4. 商户订单号带测试环境前缀，且在商户号内全局唯一，避免将来与生产订单冲突。
5. 微信支付适配器调用 JSAPI 下单接口，并提交商户号、AppID、会员 OpenID、整数分金额、人民币币种和通知地址。
6. API 请求使用商户私钥签名，证书序列号使用商户 API 证书序列号。
7. 微信成功返回 `prepay_id` 后，API 保存支付方引用并把订单改为 `pending_payment`。
8. API 使用商户私钥生成小程序调起支付所需的 `timeStamp`、`nonceStr`、`package`、`signType=RSA` 和 `paySign`。

相同请求 ID重试必须返回同一订单。若调用微信后响应丢失，服务端先按原商户订单号查单，不创建第二笔微信订单。

### 5.2 小程序调起支付

1. 小程序只接受服务端返回的完整 JSAPI 调起参数。
2. 小程序调用 `wx.requestPayment`。
3. `success` 只表示微信客户端流程完成，不能直接增加余额。
4. 无论客户端返回成功、取消还是网络异常，小程序都查询服务端订单状态。
5. 页面只在服务端返回 `settled` 后刷新余额和历史记录。
6. `pending_payment` 显示“支付结果确认中”，允许稍后重新查询。

### 5.3 支付通知

通知控制器必须取得未经 JSON 重新序列化的原始请求体，并按以下顺序处理：

1. 读取微信支付时间戳、随机串、签名和微信支付公钥 ID。
2. 使用本地配置的微信支付公钥验签，并拒绝未知公钥 ID。
3. 使用 APIv3 密钥对通知资源执行 AES-256-GCM 解密。
4. 只接受成功支付事件。
5. 校验商户号、AppID、商户订单号、微信支付单号、币种和实付金额。
6. 将微信通知 ID、载荷哈希和支付单号送入现有统一结算边界。
7. 在同一 PostgreSQL 事务中写入通知收件箱、充值本金/赠送账本、会员权益来源、审计、云事件和订单 `settled` 状态。
8. 重复通知返回成功，但不重复写入钱包或会员权益。

验签、解密或业务字段校验失败时不入账，并记录不包含密钥、明文敏感字段或完整签名材料的安全日志。

### 5.4 主动查单与超时

服务端提供按会员身份和本地订单号查询订单状态的接口。对于 `pending_payment` 订单，服务端可按商户订单号调用微信查单：

- 微信返回支付成功时，复用与通知相同的统一结算边界。
- 微信返回未支付时保持等待。
- 微信明确返回已关闭时标记 `expired`。
- 到达本地 15 分钟期限时，先查单；确认未支付后调用关单，关单成功后才标记 `expired`。
- 已收到真实成功支付的订单即使通知延迟，也必须结算，不能只因本地时钟超时而拒绝入账。

这避免出现“微信已扣款但测试钱包没有到账”的资金悬挂。

## 6. 密钥和证书

敏感材料仅部署到服务器的受限目录，例如：

`/opt/zyapp/secrets/wechatpay`

包括：

- 新的 APIv3 密钥
- 商户 API 证书
- 商户 API 私钥
- 微信支付公钥
- 微信支付公钥 ID

要求：

- 私钥和 APIv3 密钥文件权限为 `0600`。
- 密钥目录不进入 Git，不进入 Docker 镜像，不复制到小程序包。
- 测试 API 以只读挂载方式读取文件。
- 环境配置只保存非敏感的商户号、AppID、证书序列号、文件路径和支付模式。
- APIv3 密钥通过专用 secret 文件读取，不写入普通环境文件。
- 日志、测试夹具、截图和错误响应不得输出密钥、私钥或完整支付报文。
- 已重置的旧 APIv3 密钥不再使用；部署时只接受新的密钥文件。

本地 `E:\证书\API证书` 和微信支付公钥文件只作为部署来源，不移动、不覆盖原文件。部署脚本不得读取或回显密钥正文。

## 7. 组件边界

新增或调整的组件保持单一职责：

- 微信支付配置：校验模式、商户标识、证书序列号和 secret 文件路径。
- 请求签名器：生成 API v3 Authorization 和小程序 `paySign`。
- 微信应答验证器：验证微信响应头签名和公钥 ID。
- 通知解密器：只负责验签后的 AES-GCM 资源解密。
- 微信支付 HTTP 适配器：JSAPI 下单、查单和关单。
- 充值应用服务：订单状态机、身份和金额校验、统一结算。
- 通知控制器：保留原始请求体，转换为经过验证的支付事件。
- 小程序支付服务：封装 `wx.requestPayment` 与状态轮询。

支付密码学代码不直接写数据库；充值应用服务不直接拼装微信签名；小程序不持有任何商户秘密。

## 8. 错误处理和可观测性

- 微信下单暂时失败：订单进入可重试状态，使用原请求 ID 和商户订单号恢复。
- 用户取消：订单保持待支付，页面显示已取消；服务端仍允许后续查单确认。
- 客户端断网：恢复网络后按本地订单号查询，不重新创建订单。
- 微信通知重复或乱序：通过通知 ID、载荷哈希、支付单号和订单锁实现幂等。
- 金额、商户号或 AppID 不匹配：拒绝入账并产生安全告警。
- 未知微信公钥 ID：拒绝验签，等待管理员更新可信公钥配置。
- 数据库事务失败：通知返回失败让微信重试，不能先确认通知再异步记账。
- PC 暂时离线：云端账本先完成，既有下行事件最终把增量合并到 PC，不覆盖 PC 当前余额。

日志使用内部订单 ID、商户订单号后缀、事件类型和错误分类进行关联；手机号、OpenID、密钥和完整签名不进入日志。

## 9. 测试策略

实现遵循测试驱动，先写失败测试再写生产代码。自动化测试使用临时生成的 RSA 密钥和合成通知，不使用真实商户密钥。

至少覆盖：

- API v3 请求规范串和 Authorization 签名。
- JSAPI `paySign`。
- 微信响应验签和错误公钥 ID。
- 通知验签、AES-GCM 解密和篡改拒绝。
- 商户号、AppID、币种、订单号和金额不匹配拒绝。
- 同一通知重复到达只产生一笔钱包流水。
- 通知与主动查单并发只结算一次。
- 下单响应丢失后按原订单号恢复。
- 用户取消、客户端断网和查询恢复。
- 超时前查单、关单和迟到成功支付处理。
- 1 分测试档位仅在测试 API 显式开启时可用。
- 生产化测试构建拒绝 HTTP、Mock 和虚拟手机号。
- 小程序只有拿到真实 JSAPI 参数时才调用 `wx.requestPayment`。
- 小程序不会调用 Mock 结算端点。

自动验证包括共享契约、API 测试、API 构建、小程序类型检查、小程序测试、小程序生产化测试构建、Caddy 配置校验和四个公网健康地址。

## 10. 人工验收

自动化验证通过后，由小程序账号所有者完成：

1. 在微信公众平台配置 `https://judian.icu` 为 request 合法域名。
2. 在微信开发者工具中使用正式 AppID 导入构建结果。
3. 确认项目开启合法域名校验。
4. 真机完成微信登录和手机号授权。
5. 核对余额、月卡和历史记录来自测试门店、测试数据库。
6. 发起 0.01 元真实支付并完成付款。
7. 在微信支付商户平台确认该笔交易。
8. 在小程序确认测试钱包本金增加 1 分、赠送为 0。
9. 重复刷新和查询，确认余额不再次增加。
10. 确认 PC 的 IP 生产/测试连接均未受域名部署影响。

小程序预览、真机授权、实际付款、隐私声明、微信审核和正式发布必须由账号所有者参与；自动化或模拟器结果不能替代这些验收。
